# 14 · 人话层与移动版

> **状态：已实现（P26–P28）。**
>
> 本层**不改动任何现有引擎**，只新增一个消费者。四柱、六爻、六壬、奇门
> 照旧产出术语版；人话层读它们的**判定**，产出平常话，并把术语原文挂在旁边。

---

## 0. 一句话

**人话是判定枚举的函数，不是逐盘自由撰写。**

每条人话都由一个枚举值查表得到（旺衰档、象限、五行状态、节点方向、爻力五档）。
于是它不可能漂离技术层 —— 想改人话，得先改那个枚举的含义。
逐盘自由撰写读起来更自然，但那一层一旦松动，「报告不做新判断」就守不住了；
而人话层恰恰最容易松动，因为它读起来本就不像在下判断。

---

## 1. 去掉术语，恰恰去掉了天然的对冲

这是整层的设计前提，其余每一条都从它推出来。

| | |
| -- | -- |
| 技术层 | 「用神取木，喜水」—— 晦涩，读者一眼就知道自己在看一个模型 |
| 人话层 | 「你适合往东发展」—— 具体、可执行，读起来像忠告 |

**同一份判定，换个说法就从「模型的输出」变成了「对你的建议」。**

所以人话层需要的是**更严的约束，不是更松的**。这一点与直觉相反，
也是这一层最容易做错的地方。

### 1.1 第二人称的取舍

技术层有一条 `zh.secondPerson.address`，禁掉报告正文里所有的「你」，
理由是「第二人称把结构描述变成了对读者的断言」。

人话层偏偏要用「你」—— 那是它平易近人的来源。但上面那条理由并没有失效，
只是转移了。故人话层的做法是：**放开第二人称，同时补上六条更硬的**，
技术层其余十九条**一条不减**。

三种做法之中选了第三种：

| 做法 | 否掉的理由 |
| -- | -- |
| 人话不用「你」，改无主语句式 | 守卫一条不改，但平易近人打折扣 |
| 用「你」，整体豁免 secondPerson | 豁免一开，其他规则容易被顺手豁免。本项目已经见过一次「加了新出口忘了配守卫」 |
| **用「你」，另立一套更严的** | ✅ 承认「人话更危险」，而不是绕开它 |

## 2. 六条人话专有禁令（`plain/guard.ts`）

| 规则 | 拦什么 | 为什么 |
| -- | -- | -- |
| `zh.plain.actionable` | 方位、属相、颜色、数字、日期这类可以照着做的指定 | 技术层本就不产出，人话层更不许「翻译」出来 —— 那等于凭空造了一条建议 |
| `zh.plain.fitness` | 「适合／不适合」做什么工作、行业、结婚、投资 | 一套按出生时刻推演的模型给不出适配判断，而人话读起来最像它给得出 |
| `zh.plain.imperative` | 「不妨」「记得」「建议你」这类祈使 | 第二人称 + 祈使 = 忠告 |
| `zh.plain.appearance` | 相貌评价、五官、美丑 | 从出生时刻断相貌比断性格更接近伪科学的人身判断 |
| `zh.plain.otherPerson` | 「你的配偶多半是……的人」 | 用一个人的盘描述另一个人，是把推演套在没同意过的第三方身上 |
| `zh.plain.framing` | 术语漏出而同段没有说明它来自一套传统模型 | 不说明，读者会把它当成对自己的鉴定 |

### 2.1 依据块是引文，不是人话

「看依据」里放的是**技术原文**，含术语是它的本分。但守卫按**段**判定，
看不到上一行的小标题，故引文须自带标示 —— 命令行版渲染为
`- 〔推演〕原文…`，那两个字既是给读者的标示，也让框定语落在同一段里。

### 2.2 一处修过两次的 bug

`zh.plain.framing` 的繁体版初稿只把 `context` 转成繁体，没有**简繁双写**。
后果：触发词多为简繁同形（五行、命理、八字），框定语却不同形，
于是**繁体规则在简体正文上必然误报「缺框定语」**。

这个 bug 在 `report/guard.ts` 修过一次（P17），手写派生时又犯了一遍。
现已改为复用那边的 `biscript`。

## 3. 每张卡挂着它的来历

```ts
interface PlainCard {
  id: string;
  section: "性格" | "身心" | "亲近的人" | "人生轨迹" | "起伏" | "今年" | "本月" | "今天";
  title: string;
  body: string;                        // 人话，由枚举查表拼成
  evidence: readonly NarrativeLine[];  // 报告**原文**，不重写不缩写
  confidence: number;
}
```

一张卡 ≠ 一句技术叙述。「你的底子偏轻」概括的是旺衰、通根、党势三条判定，
故卡片与技术叙述是**多对一**。`evidence` 是这一层最要紧的诚实性保证：
人话是概括，而读者随时能看到被概括的是什么。

**「看依据」不是可选装饰，是结构的一部分。** 测试断言：绝大多数卡片
（>85%）有依据可看，且每条依据都能在报告里**原样**找到。

### 3.1 三个实现时才发现的错

- **「身心」误用了「场合」的词表**，得出「需要被看见的场合上，这一路偏盛」
  这种范畴错误的句子。身体那一路改用《内经》的脏腑对照，另立一张表
  （`ELEMENT_BODY_PLAIN`），并写成测试：两张表逐项不得相同。
- **六亲与大运的依据按模板 id 前缀找**，于是五条六亲共用同一条依据、
  十几步大运各自挂着全部叙述。模板 id 只表象限与类型，不含序号，
  故须**按下标对齐**。
- **大运依据整体错开一格**（`LuckStep.index` 自 1 起而数组自 0 起）。
  错开一格最阴险：每张卡都有依据，只是全是隔壁那一步的，
  看上去毫无异样。已写成断言：第 n 步的依据文本必须含「第 n 步」。

## 4. 三处内容边界（人工决定，非技术判断）

| 项 | 做法 | 理由 |
| -- | -- | -- |
| **长相** | 只出**形体倾向**（偏热偏干、五行虚实），不出五官、不作美丑之评 | 从出生时刻断相貌比断性格更接近伪科学的人身判断 |
| **朋友／亲人** | 只出「你与这类关系的**相处结构**」，不描述对方是什么人 | 用一个人的盘描述另一个人，是把推演套在没同意过的第三方身上 |
| **按年的事件** | 只出「那一年的结构与本命契合到什么程度」，不列事件 | 模型给不出「会发生什么」。这个差别在人话里最容易糊掉，故正文里明写 |

## 4.5 起伏与时间：指事只说类别

「2018–2020 年，父母可能有问题」这样的句子是**事件预言**，措辞守卫会拦，
而且它本就越过了这套模型能说的范围。故起伏卡片写成：

> **2018–2020 年** —— 与长辈、学业、被照顾相关的那一路，这段时间这一项是顺风的。

时间段与「指向哪一类事」都从节点的 `evidence` 里取（`进入`/`退出` 与
`node:tenGod.正印` 这样的溯源串），**不在人话层另算一遍**。
十神与宫位各有一张「指向哪一类事」的表（`GOD_DOMAIN_PLAIN`、`PALACE_DOMAIN_PLAIN`），
认不出的序列 id 返回 null —— **不瞎猜，认不出就不说这一句**。

流年流月的神煞指事同理：`ShenshaHit.narrativeTags` 本就带着「金舆 → 车马、
配偶助力、安逸」这类指事，人话层照搬并加一句「这是说这些符号在传统上与哪类事
相联系，不是说这些事会发生」。

那句「是排序不是概率」放在**小节**说一次（`sectionNotes`），不在每张卡上重复 ——
八张卡各说一遍，读者会跳过它，而它恰恰是最不该被跳过的一句。

## 4.6 人话由谁生成：代码档与 AI 档

| 档 | 怎么来 | 特点 |
| `code`（默认） | `plainCards` 的定值映射：判定枚举查表，过人话守卫，逐条挂技术依据 | 可复算、逐字稳定、全在本机 |
| `ai` | 交给 `bazi-plain` Skill 转述 | 措辞更活，但它是语言模型不是查表，两次转述未必一字不差 |

⚠️ **AI 档不自动把数据送出去。** 本站纯静态、生辰数据不出本机；
若在浏览器里直连模型接口，等于把出生信息发给第三方，与全站的隐私纪律相反。
故 AI 档只把技术报告与那六条规矩拼成一段可复制的文本 ——
送不送、送给谁，是用户的决定，不是这个应用替他做的。

## 5. 免责声明是改写，不是删减

人话版的声明（`PLAIN_DISCLAIMER`）四个要素一个不少：
文化研究与自我省思的定位、不具备预测能力、不构成专业建议、导向持证专业人士。

之所以不直接复用技术版：那一版说「本报告为四柱命理的计算实现」，
在一个刻意不出术语的应用里既突兀，又把「命理」二字漏了出来。

**但改写声明是件危险的事** —— 很容易在「说得通顺些」的名义下弱化它，
故把四个要素写成测试逐条断言，并在界面上保留「看原文」，
让改写过的东西旁边永远躺着原件。

## 6. 移动版（`/m`）

四个标签，对应两组功能：

| 页 | 内容 |
| -- | -- |
| 我 | 采集出生信息（时辰未知则明说，不猜）→ 性格、身心、亲近的人、人生轨迹、起伏 |
| 时间 | 今天、本月、今年、按年；今天另附「还有另一套说法」（四柱 ∥ 六爻并列，不合并） |
| 问事 | 32 类占事，一事不二占落在 localStorage，问题只存指纹 |
| 关于 | **把这个应用不能做的事写清楚** |

「关于」页刻意做成一个标签而不是折叠在角落：
人话版最大的风险是**读起来像结论**，术语版靠晦涩自带对冲，人话版没有，只能明说。

配色沿用全站的中性色板 —— **卡片一旦染上红绿，「顺／逆」立刻被读成「好／坏」**，
而顺逆衡量的是结构契合度，不是运气好坏。

移动版与桌面版**不共用页面**：桌面版给愿意读术语的人，移动版给不读术语的人，
硬塞进同一套组件里通常是两边都不好用。共用的是同一个 `@fate/core`。

## 7. 命令行与 Skill

`fate plain --chart c.json [--section …]` 输出「一句人话 + 缩进的依据」两层。
**命令行没有「点开」这个动作**，若只出人话，那层来历就等于不存在了。

`Io.out` 的 `kind` 增加了 `plain` 一档：人话版走 `scanPlain`，技术版走 `scanText`。
拿技术层的规则去扫人话，会把每一个「你」都拦下来；反过来则漏掉第二人称那条红线。
**这是「新出口要配自己的守卫」第三次出现**（前两次：繁体、六爻问事）。

`@fate/skill-plain` 是与 `@fate/skill` 并列的第二个 Skill，共用同一台引擎。
它的职责是**转述而不是翻译** —— 引擎已经把判定映射成了平常话且过了守卫，
模型自己从术语版翻一遍，等于绕开那两层。

Skill 里写死的一条：**复述时不要「润色」得更肯定**。
把「偏轻」改成「很弱」、把「传统上」删掉、把置信度提示省略，
读起来都更顺，也都越了界。
